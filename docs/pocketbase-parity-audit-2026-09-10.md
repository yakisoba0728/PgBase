# PocketBase 1:1 기능 대비 감사 — 2026-09-10

> **대체 안내:** 기능 단위 79행, **PgBase 구현 상태와 PB 동등성의 분리 판정**, 정정된 집계는 [정밀 감사](pocketbase-parity-detailed-audit-2026-09-10.md)를 기준으로 한다. 이 문서는 당시 32행 요약 기록이다.

## 결론과 비교 기준

이 문서는 “같은 이름의 기능이 있는가”가 아니라, PocketBase 사용자가 관찰하는 입력·출력·제약·확장 계약을 비교한다. **PgBase는 PocketBase의 무수정 대체품이 아니다.** PostgreSQL/UUID/typed schema/keyset cursor/명시적 서비스 경계를 택했으므로, 일부 차이는 의도된 비호환이다.

- **PocketBase 기준:** 공식 `pocketbase/pocketbase`의 `v0.40.3`, `5684ee24f1e88f71a2ede73d20cf547fbd509e16` (2026-09-06). 로컬 `.local/upstream/pocketbase`에서 태그와 `origin/master`가 같은 SHA임을 확인했다. 따라서 이 감사에서 stable과 upstream main 사이의 별도 소스 차이는 없다.
- **PgBase 기준:** 이 감사의 시작점은 `3f618ed99eb911cbfe0731e03384f925137c60ed`; 후속 구현은 `c75ec2e`와 `99a9700`에 기록했다. `origin/main`은 `53a474143e117251d9b322441508ac85d776ef2a`이다. N6–N9 소스는 PR #35로 main에 병합됐지만, 로컬 설치는 여전히 schema 40/N1–N5 상태다.
- **근거 방식:** 양쪽 고정 SHA의 소스 entry point와 PgBase checked-in test를 읽었다. 이 문서의 “검증”은 해당 테스트가 존재하고 과거/현재 실행 근거가 문서화됐다는 뜻이며, 이번 감사에서 외부 provider, 실제 Windows, 전체 PocketBase suite, live 설치 DB에는 실행하지 않았다.

### 판정

| 판정 | 뜻 |
| --- | --- |
| 동등 구현·근거 충분 | 같은 사용자 목표와 핵심 경계가 구현되어 있고 직접적인 PgBase 테스트 근거가 있다. PB wire/API/SDK 호환까지 뜻하지 않는다. |
| 구현됨·동등성 근거 부족 | 기능은 소스에 있으나 PB의 모든 입력/오류/운영 경계를 대조하거나 실행하지 못했다. |
| 부분 구현/차이 | 공통 목표는 제공하되 PB 기능·문법·한계·수명주기가 다르다. |
| 미구현 | 관련 PgBase API/UI/서비스를 찾지 못했으며, PB 사용 사례를 그대로 수행할 수 없다. |
| 설계상 비호환/범위 밖 | PgBase가 의도적으로 다른 모델을 채택했다. 필요하면 별도 호환 계층이 필요하다. |
| 판단 불가 | 소스 또는 안전한 실행 근거가 부족하다. |

“완벽” 판정은 하지 않는다. 특히 API wire format, PocketBase JS/Dart SDK의 무변경 실행, SQLite 단일 파일 운영은 별도 호환성 시험 없이는 주장할 수 없다.

고정한 32개 inventory 항목의 집계는 **부분 구현/차이 22, 구현됨·동등성 근거 부족 6, 설계상 비호환 4**다. `동등 구현·근거 충분`은 0이다. 이는 PgBase에 기능이 없다는 비율이 아니라, PB와 *동일한* 공개 계약이라는 높은 기준의 집계다. Inventory는 schema/data, record API, auth, files, realtime, extension/SDK, admin UI, runtime/ops의 여덟 영역을 모두 포함한다.

## 핵심 차이의 실제 사용자 효과

### 기존 PocketBase 앱을 옮기는 경우

가장 먼저 막히는 것은 collection JSON이 아니라 HTTP와 SDK 계약이다. 예를 들어 PB client가 `GET /api/collections/posts/records?page=2&perPage=30&filter=title~'go'` 및 `{page,totalPages,items}`를 기대해도, PgBase는 다른 `/api/v1/...` route와 `{items,nextCursor}`, 최대 200개 keyset cursor, 좁은 comparison filter를 제공한다. PB JWT refresh/auth-methods, file URL/token, realtime `clientId` subscription, JS `$app` hooks도 같은 이유로 바꿔야 한다. 이는 migration adapter 없이 endpoint를 치환할 수 없는 P0 호환성 작업이다.

### PgBase 자체 제품으로 사용하는 경우

CRUD, schema planning, record rule, named realm의 password/OAuth/email OTP/TOTP, attachments, durable realtime, admin UI, JSVM, migrations와 backup은 구현돼 있고 대표 단위·통합 tests가 있다. 하지만 PB처럼 “모든 field option/관리 UI setting/외부 provider/platform에서 확인됨”은 아니다. 실제 DB migration rollback, OAuth/SMTP/S3 provider, Windows self-update, public release channel은 아직 환경별 실행 증거가 없다.

### 의도적으로 다른 운영 모델

PocketBase는 SQLite data directory, persisted singleton settings, in-memory topic broker와 extensible dynamic model을 중심으로 한다. PgBase는 PostgreSQL schema/catalog, startup options, durable collection event outbox와 typed service APIs를 중심으로 한다. PgBase의 ETag/idempotency/receipt/physical catalog checks와 PB의 raw SQL view, dynamic model hook, runtime settings를 단순히 우열로 환산하면 안 된다. 사용 사례별로 어느 쪽 contract를 채택할지 정해야 한다.

## 우선 보완 백로그

1. **PB 호환 목표를 먼저 결정한다.** 완전 wire/SDK 호환이 목표라면 R1–R3/A1/RT1/X4를 묶어 versioned compatibility layer와 PB conformance fixtures부터 설계해야 한다. 현 API에 필드만 덧붙이면 호환이 생기지 않는다.
2. **고객 영향이 큰 query gap을 줄인다.** filter operators/any-match/time functions, offset pagination+total, `fields` projection을 명시적으로 채택·거절하고, 채택 시 PB request/response golden tests를 만든다. 현재 PB client migration의 가장 큰 즉시 장애다.
3. **field/collection 세부 계약을 inventory화한다.** PB field별 validation/default/serialization/index/file option을 하나씩 PgBase schema/API/UI에 매핑한다. select/date/editor/geo/file thumbnail cardinality와 view SQL은 “부분 지원”이라고만 두면 사용자 예측이 어렵다.
4. **auth/OAuth 호환과 운영 UI의 실제 시나리오를 검증한다.** PB provider catalog·template settings·token duration을 도입할지 결정하고, reset/verify/OAuth/MFA/browser/admin flows를 provider fixture로 실행한다. PB logs/settings/cron/export 화면은 메뉴 존재 대신 import/export·recovery 시나리오로 비교한다.
5. **platform/release/staging 검증을 분리한다.** schema40→41 disposable upgrade/rollback, actual Windows updater, public artifact signature/channel, external SMTP/OAuth/S3는 아직 실행 근거가 없다. 운영 환경/credential/target release가 정해진 뒤 수행한다.

## 이번 감사의 검증 한계

- PocketBase 전체 Go/UI 테스트, PgBase 전체 CI, 실제 PostgreSQL integration, browser E2E, Windows, cloud/provider는 이번에 실행하지 않았다. 현재 호스트의 `PGBASE_TEST_ADMIN_URL`과 Docker daemon 부재 때문에 새 disposable PostgreSQL 검증도 하지 않았다.
- 이전 N6–N9 acceptance의 “focused test passed”는 제품 소스 근거로 참고했지만, 그 자체로 PB parity를 증명하지 않는다. SQL console의 reload/commit-unknown focused UI/backend tests는 있으나 실제 browser restart/TTL E2E는 미실행이다.
- 비교 대상 upstream은 확인 시점의 `v0.40.3`/`master` 동일 SHA다. 이후 upstream 변경은 이 문서의 판정에 자동 반영되지 않는다.

이번에 새로 실행한 읽기 중심 검증은 `go test ./internal/api ./internal/query ./internal/recordops ./internal/userauth ./internal/schema ./internal/filestore`이며 모두 통과했다. PostgreSQL이 필요한 integration test는 이 명령에 포함되지 않는다.

후속 배치에서 `go test ./internal/api ./internal/query ./internal/recordops ./internal/schema` 및 같은 네 package의 `go test -race`도 통과했다. R3/D3의 새 live integration tests는 compile까지 확인했지만 `PGBASE_TEST_ADMIN_URL`가 없어 실행 전 중단됐다.
