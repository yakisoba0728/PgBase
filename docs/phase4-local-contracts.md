# P8 local implementation and acceptance

P8 extends the P7 baseline (`701256b`, schema v32). It was merged through
[PR #32](https://github.com/yakisoba0728/PgBase/pull/32) as `0d28446` after all five required CI jobs passed, then installed into the
existing local PostgreSQL 17 project at schema v38. Product source, local
installation and public release remain distinct; no P8 public release was made.

The comparison target is the locally pinned PocketBase v0.40.3 source. These are
PgBase implementations with PostgreSQL transactions, UUID identifiers, and
revocable sessions. They do not provide PocketBase wire or extension API
compatibility.

## Fields and administrator editing

[Advanced fields](advanced-fields.md) describes editor, geoPoint, autodate, and
ordinary password fields. Schema planning, record writes, API responses,
TypeScript types, and administrator forms use the same contracts. HTML source
remains a string; the rich editor serializes its supported document model when
visually edited. GeoPoint has two numeric coordinates and an offline map.
Autodates are generated by the server. Passwords are hashed and omitted from
browser drafts and record duplication.

Validation includes a real 5 MiB HTML create/get/list/batch HTTP round trip,
coordinate filters and cursors, transaction retry/rollback, public Go password
verification, and browser editing. A separate PostgreSQL test renames all four
field types on populated data, preserves physical field identity and values,
checks a dependent View, and exports/imports the resulting schema into a fresh
database. JSON object key order is immaterial to that portable contract.

## Uploaded-file storage

[Storage settings](storage-settings.md) covers encrypted persisted S3 settings,
connection testing, and durable object migration. Changing destinations requires
copying and verifying referenced objects before activation. The migration ledger
supports restart, resume, cancellation, and delayed cleanup that preserves a
namespace reused by a later migration.

The browser generates and remembers an operation UUID before sending Start.
Retries use that same ID; the server rejects different input under an existing
ID. An uncertain response is recovered by the exact ID. Latest-migration lookup
also allows discovery from another page. Only the operation ID is written to
session storage; destination credentials remain in memory.

The administrator workflow has been exercised with a real file copied from
local storage to MinIO and back, checking the downloaded bytes at each stage.
The test also discards a successful Start response and verifies recovery without
submitting a second operation. Unit tests exercise transient status and settings
refresh failures, preview invalidation, and failed-job recovery.

## User migrations and Go hooks

[User migrations](user-migrations.md) are compiled Go callbacks with source
checksums and a separate applied-history ledger. The public CLI supports template
generation, listing, Up, and Down from an external Go project. Each callback and
history change are transactional, serialized with schema operations, and checked
against managed physical schema before commit. A real schema Apply waiting behind
an active user migration rejects its stale plan after the migration commits; no
partial DDL is published and the shared cache reflects the committed version.
Cancellation and failed Up/Down roll back transaction work. Trusted Go callbacks
cannot make independent SQL connections or external effects rollback-safe.

[Lifecycle mapping](lifecycle-parity.md) records implemented app, collection,
authentication, realtime, storage, and backup events and their precise
differences from PocketBase. Before callbacks can veto eligible operations;
After callbacks observe their final outcome. Retryable callbacks must not perform
irreversible external effects. These hooks do not guarantee durable external
delivery.

## Local acceptance

Final local verification passed Go unit/race and the PostgreSQL 18/MinIO
integration suite with the skip policy. The broad run exposed an ordering
assumption in the backup lifecycle test: receiving After did not mean the worker
had released its reservation. The test now waits for worker exit; a 100-run race
check and a complete backup-package rerun cover that final test-only change.

UI 489/489, typecheck/build, the full authenticated browser suite 19/19, and the
three P8 browser scenarios after the final backup-probe fix passed. These browser
counts overlap. TypeScript unit tests, live HTTP conformance and npm pack passed.
Lint reported zero issues; unit/integration vet, six platform builds, OpenAPI's
146-route contract, immutable migrations 1–32 and embedding of 33–38 passed.
Measured repository ceilings are recorded below.

Backup S3 is separate from uploaded-file storage. An actual S3-backed snapshot
was restored through lower-level RestoreNew followed by restored-storage reset
after deleting its source object. The restored local bytes matched, settings
contained no S3 secrets and the source object remained absent. Managed startup
resets inherited storage work before starting the restored candidate.

The populated upgrade check used the installed v32 CLI/API to create four records
in two related collections in an isolated copy. Upgrading that copy to v38
preserved hashes and row counts and passed doctor. Local test logs live under
`.local/verification/phase4-*`; the regression sources and commands are committed.
After merge, the original database, files, existing backup archives, environment
and executable were preserved in a private pre-upgrade backup. The local v32→v38
upgrade passed doctor/readiness, administrator login, all four field previews,
local file/backup storage probes and a PostgreSQL 17 managed backup download with
manifest sizes and SHA-256 verified. Installed product commit: `0d28446b4003679465103c5fe2d4f1c65364cc79`.
See [project status](project-status.md) and [TODO](../TODO.md).

JSVM, Dart SDK, the SQL console and self-update remain subsequent implementation
work. External cloud deployment, production provider accounts and public package
publishing remain outside the local-only scope.

## Independent review

Standards review found no mandatory breach in the inspected changes. It recorded
optional improvements to the backup lease tuple, explicit credential-state
validation, migration state names, and manager receipt locking. Manager release
and the backup UI port were expanded into ordinary readable blocks. The remaining
design suggestions do not establish an incorrect runtime behavior and are not
reported as completed refactors.

Spec review reproduced startup recovery racing another backup publisher and
strict-metadata/foreign-object cleanup gaps. Recovery now shares transition and
backup-ID locks, re-reads durable state, and retains incomplete pending work.
Owned receipts require valid bounded JSON, identity, size, and digest. Orphan
cleanup requires the archive's matching S3 ownership metadata. The operator must
quiesce possible stale publishers before explicitly discarding a pending ID;
startup does not infer that a missing database session means remote I/O stopped.
Focused two-controller, lost-session, MinIO and restore regressions cover these
fixes. Local acceptance is recorded above; merge and installation are tracked in TODO.
