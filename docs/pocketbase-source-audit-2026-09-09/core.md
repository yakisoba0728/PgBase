# PocketBase v0.40.3 core and migrations source audit

> **Source-reading audit complete.** This document compares source contracts. It is not runtime validation, a compatibility certification, or evidence that either product has been exercised against the other's test suite.

## Scope and method

The assigned scope contains 147 files in `inventory.json`: every text file under PocketBase `core/**` and `migrations/**`, including tests, at tag `v0.40.3`, commit `5684ee24f1e88f71a2ede73d20cf547fbd509e16`. The comparison target is PgBase commit `35af64c`. `core-ledger.json` records the 115 non-field files consumed in full. Its 32 `core/field*.go` entries remain `indexed` only because the independently completed [field ledger](core-fields-ledger.json) is the authoritative per-file reading record for that delegated slice; all 32 are `read` there and their contract comparison is in [core-fields.md](core-fields.md). No file in this assignment was classified as generated.

The comparison is architectural and behavioral, not a compatibility promise. PocketBase uses SQLite and an extensible in-process model/hook framework; PgBase uses PostgreSQL, explicit HTTP contracts, typed schema plans, transactional record services, and separately bounded background services. Similar user-visible features can therefore have deliberately different persistence and extension semantics.

## Overall assessment

The audited PocketBase core is broader as an embedded application framework: it combines dynamic models, field behavior, runtime settings, hooks, raw SELECT views, mail alerts, process restart, SQLite migrations and directory backup in one programmable core. PgBase overlaps strongly on schema-managed CRUD, auth collections, OAuth/TOTP, relation queries and limits, attachments and thumbnails, file tokens, realtime delivery and operational restore machinery, but it exposes fewer dynamic model, field and runtime-configuration seams.

The largest material capability differences are PocketBase's field catalog and field-specific interception, raw-SQL view expressiveness, runtime-persisted settings, administrator email alerts, and its general model/request event surface. PgBase-specific contracts visible in source include guarded schema operation identities and receipts, physical PostgreSQL manifest validation, transactional authorization with owner/service principals, membership-bound cursor pagination, bounded attachment lifecycle, and multi-major restore drills. Those are architectural differences rather than a scalar progress score. This audit establishes what the pinned source says; runtime parity, performance and migration fidelity require separate executable validation.
