# Astra 설계 결정 — 전체 2회 감사 후 개선 계획

기준 커밋: `5cb721ff5590bf89b45ea9087d2ace0b74fe7127`. 이번 단계는 감사와 계획이며 제품 코드·테스트·마이그레이션을 변경하지 않는다.

## 판정 기준

- 과거 232개 기능표는 비교 자료다. 이번 감사가 모든 기능의 무결함 또는 PocketBase 전체와의 완전 동등성을 증명하지 않는다.
- 일반 단위 테스트 통과는 새 후보의 재현 증거가 아니다. 해당 입력으로 잘못된 결과를 직접 관찰한 경우에만 동적 재현으로 표시한다.
- 정적 결함은 입력, 호출자, 방어 경로, 잘못된 결과가 코드에서 성립하는 범위를 구체적으로 적는다. 다른 계층의 계약 확인이 필요하면 확정하지 않는다.
- 같은 원인을 두 번 발견해도 한 개의 개선 항목으로 합친다. 1차와 2차 판정이 다르면 최종 근거와 보류 조건을 남긴다.
- 과거 보고서의 blob과 현재 커밋의 blob이 다르다는 사실은 결함이 아니다. 보고서가 주장하는 기준 커밋과 실제 증거가 모순되는지 확인한다.
- 큰 결과를 만든 뒤 적용하는 출력 제한은 결과를 만드는 중간 메모리 사용량을 제한하지 않는다. 반환값 한도, 처리 건수 한도, 피크 메모리, 동시성 한도를 구분한다.
- lease 기반 잡 실행은 handler의 외부 부작용까지 exactly-once로 보장하지 않는다. 취소·idempotency·fencing 계약을 명시하고 과도한 보장을 추가하지 않는다.
- 공개된 trusted/admin 원시 연산의 동작을 일반 사용자용 API 계약으로 오판하지 않는다.

## 실행 순서

| 단계 | 목적 | 승인할 변경의 형태 | 완료 조건 |
|---|---|---|---|
| 0 | 기준과 재현 고정 | 판정별 회귀 사례, 통합 테스트 fixture, API·migration 계약 기록 | 위험 후보별 실패 원인 또는 의도된 동작 확인 |
| 1 | 보안·데이터 무결성 | 인증·권한·설정 소유권·서명 검증·스키마 stale 감지의 작은 수정 | 악성/경계 입력 거부, 정상 사용 유지, race/트랜잭션 검증 |
| 2 | 자원 정리·안정성 | 업로드 cleanup, 종료 수명, 취소·폴링·URL 정리 | 실패·timeout·unmount 이후 남는 자원/갱신 없음 |
| 3 | 기능 계약 일치 | API 응답·SDK 타입·오류 전달·UI 상태의 좁은 수정 | Go/HTTP/TS/Dart/UI 계약별 같은 입력·결과 확인 |
| 4 | 유지보수·실제 중복 제거 | 증거 있는 공통 모듈, 불변식의 단일 소유자, 제한된 호출부 변경 | 공개 계약 동일, 기존 회귀 통과, 복잡도와 중복 감소 설명 가능 |
| 5 | 문서·주석·생성물 정리 | 현재 문서 진입점, 역사 자료 보관, 중복 설명 삭제, 생성 재현성 | 실제 기능과 문서 연결, 라이선스와 안전 근거 보존 |

각 단계는 여러 작은 PR로 나눈다. 같은 함수에 버그 수정과 대규모 이름 변경·파일 이동을 함께 넣지 않는다. DB checksum을 깨는 과거 migration 수정은 하지 않는다. 필요 시 새로운 순방향 migration과 복구 절차를 설계한다.

## 모듈 경계

- `internal/schema`, `internal/recordops`, `internal/query`의 트랜잭션·인가·잠금·cursor/wire 계약을 먼저 보존한다. 파일 수가 많다는 이유만으로 합치지 않는다.
- HTTP 핸들러는 요청/응답 변환을 맡고, 정책·트랜잭션 불변식은 내부 서비스가 소유한다. 실제 중복되는 파싱·오류 매핑만 공유한다.
- 상태를 발행하는 설정 객체는 mutable slice/map을 소유해야 한다. caller mutation과 concurrent reader를 함께 검증한다.
- UI 요청 취소와 stale 결과 무시는 한 화면에서 먼저 검증한다. 모든 요청을 포괄하는 추상 hook은 공통 수명 계약이 확인된 뒤에만 도입한다.
- SDK 중복은 언어별 공통 transport/인증 흐름의 실제 동일 부분만 모은다. 브라우저 redirect, SSE 재접속, 파일 업로드 계약은 보존한다.
- 메모리 개선은 반환/부분 실패/정렬 의미를 유지해야 한다. `findAll`을 임의로 잘라 반환하거나 `deletePrefix`의 부분 삭제 의미를 몰래 바꾸지 않는다.

## 코드 줄과 주석

줄 감소 목표 수치를 먼저 정하지 않는다. 각 작업에 추가/삭제 LOC, 예상 순감소, 신뢰도, 보존 기능을 별도로 기록한다. 생성 번들/lockfile/증거 JSON 압축을 제품 유지보수 개선 수치로 합산하지 않는다.

삭제 후보: 코드 자체를 그대로 반복하는 주석, 이미 무효인 설명, 중복 단계 기록, 별도 문서로 옮길 장문의 과거 작업 일지. 보존 대상: 잠금 순서, 취소와 detach의 이유, 인증·비공개 응답 규칙, 데이터 보존, 공개 API 계약, migration checksum, 라이선스 및 생성 표시.

## 검증과 되돌리기

- 각 버그는 좁은 회귀 테스트를 먼저 확정한다. fixture 없는 단위 테스트의 통합 테스트 skip을 통과로 과장하지 않는다.
- 설정 aliasing과 종료 동시성은 적절한 race 검사, SQL/cleanup/restore는 PostgreSQL 통합 검증, UI 수명은 늦게 도착하는 응답 테스트, SDK는 실제 HTTP 실패 응답 테스트를 사용한다.
- 기능별 검증 뒤 해당 PR의 필수 CI를 통과시킨다. 변화 없는 검사를 반복 실행하지 않는다.
- 가역적 리팩토링은 PR 단위 revert가 가능하게 만든다. 데이터 변환은 사전 점검·백업·복구 검증을 포함하며 되돌릴 수 없는 변환을 단순 코드 revert로 설명하지 않는다.

## 감사 증거의 한계

coverage는 파일·blob·구간·검토자와 누락을 검사한다. 모델이 실제 모든 내용을 이해했는지는 자동 증명하지 못한다. 형식적 동일 문장, 잘린 출력, 빈 결과 파일은 완료 증거로 인정하지 않는다. 재검토·교정 이력을 보존하고 해결되지 않은 범위는 완료로 집계하지 않는다.
