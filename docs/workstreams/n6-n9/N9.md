N9에는 DB durable state가 없다. file journal은 executable의 canonical directory 안 N9 state directory에만 두며 system migration 41을 요구하지 않는다. 이 판단이 바뀌면 코드보다 먼저 integration lead가 번호와 shared ownership을 배정한다.

## 2. 구현 단위와 public contract

G3 승인 뒤 새 파일은 아래처럼 N9 private surface에 한정한다. 정확한 file split은 800-line limit과 platform build tag에 맞춰 조정하되, N6/N7/shared runtime 파일을 수정하지 않는다.

| 단위 | 책임 |
| --- | --- |
| `internal/buildinfo/` | `Version`, full Git commit, build time, supported schema range, `runtime.GOOS`/`GOARCH`를 immutable JSON record로 만든다. release build는 all fields를 link-time inject하고 source build는 `dev`/`unknown`을 정직하게 보인다. |
| `internal/selfupdate/manifest.go`, `trust.go` | strict manifest v1 decode, duplicate/unknown-field rejection, exact-byte Ed25519 verification, key parsing, version/channel/platform candidate selection. |
| `internal/selfupdate/download.go` | local immutable input and actual HTTPS retrieval, origin/redirect/deadline/byte limits, cancellation, streaming SHA-256/size validation. |
| `internal/selfupdate/journal.go`, `replace_*.go`, `lock_*.go`, `probe.go` | same-directory staging, lock, durable journal, Unix/Darwin or Windows replacement, candidate probe, recovery and verified rollback. |
| `internal/cli/version.go`, `internal/cli/update.go` | the command grammar, JSON/progress/error mapping and redaction only. It owns no updater policy outside the library. |
| `internal/selfupdate/testdata/` and N9-only test helper | ephemeral Ed25519 test key generated at test runtime, manifest signer, TLS server, old/new fixture binaries and fault injection. No private key is committed. |

The intended command surface is:

```text
pgbase version --json
pgbase update check  (--source HTTPS_MANIFEST_URL | --manifest FILE --signature FILE) --trust-key FILE [--channel stable] [--version VERSION] [--ca-file FILE] [--timeout 2m] [--max-download 512MiB] [--allow-insecure-loopback]
pgbase update apply  (same source and trust flags) [--allow-downgrade] [--state-dir DIR]
pgbase update status [--json] [--state-dir DIR]
pgbase update rollback [--state-dir DIR]
```

`version --json` is network- and DB-free and emits exactly the stable fields `version`, `commit`, `builtAt`, `goos`, `goarch`, `schemaMin`, and `schemaMax`. `check`, `apply`, and `status --json` similarly have a documented schema version and stable string error codes; human progress goes to stderr and JSON goes only to stdout. Proposed codes are `invalid_input`, `untrusted_manifest`, `unsupported_platform`, `no_update`, `downgrade_refused`, `download_interrupted`, `download_limit`, `replace_busy`, `replace_failed`, `probe_failed`, `rollback_failed`, `recovery_required`, and `migration_required`. Diagnostics never print URL credentials, private-key bytes, a full unredacted filesystem path from a user-controlled URL, or artifact contents.

The normal nonzero convention stays aligned with the existing CLI: malformed command/configuration is exit 2; a valid operation that cannot safely complete is exit 1. `no_update` is successful exit 0; unsupported platform is a deliberate exit 1 result with its stable code, not a silent fallback.

### Settings and trust input

There is no server setting, admin HTTP endpoint, database setting, background timer, or environment-only trust root. Every remote `check`/`apply` requires `--trust-key FILE`; the file is a regular non-symlink file containing exactly one base64-encoded 32-byte Ed25519 public key after a single trailing newline is removed. The command records the SHA-256 key fingerprint in its journal/status but never persists an arbitrary downloaded key as a trusted root. Key rotation is a later operator action that supplies a new explicit key and verifies a manifest signed by it; a key embedded in a manifest has no effect.

`--state-dir` defaults to `.pgbase-update` directly below the canonical executable directory. The directory, lock, journal, staged candidate, backup, and saved verified manifest/signature must be regular/non-symlink paths owned by the update operation. An explicit state directory must resolve inside that executable directory; a path outside it, a symlink, an unexpected file type, or an inaccessible install directory fails closed. This both preserves one installation's evidence and prevents a broad arbitrary-path writer seam.

The update target is the canonical executable returned from `os.Executable`, resolved once before lock acquisition; its final `Lstat` must be a regular non-symlink file. The command refuses a launcher/symlink installation rather than replacing a link target unexpectedly. Candidate and backup are created in the same canonical directory, so the Unix publication rename does not cross filesystems.

## 3. Signed manifest and selection

The signer signs the exact bytes served or read as `manifest.json`; JSON reserialization is forbidden. `manifest.ed25519` is a detached base64 encoding of exactly 64 signature bytes. The verifier decodes bounded raw bytes, checks key/signature length before calling `crypto/ed25519.Verify`, and parses only after signature success. Go documents `Verify` as validating a signature for a public key and notes that wrong public-key length panics, so the explicit length check is part of the contract. [Go Ed25519](https://pkg.go.dev/crypto/ed25519#Verify).

Manifest v1 has the following signed shape. All names are ASCII identifiers; any unknown field, duplicate release, duplicate `(version, goos, goarch)`, duplicate channel, noncanonical digest, invalid URL, non-positive size, or range that cannot parse is rejected.

```json
{
  "schemaVersion": 1,
  "channel": "stable",
  "releases": [
    {
      "version": "v0.2.0",
      "commit": "0123456789abcdef0123456789abcdef01234567",
      "minUpdaterVersion": "v0.1.0",
      "schema": {"min": 40, "max": 40},
      "artifacts": [
        {
          "goos": "darwin",
          "goarch": "arm64",
          "url": "https://releases.example.invalid/pgbase-v0.2.0-darwin-arm64",
          "size": 12345678,
          "sha256": "0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef"
        }
      ]
    }
  ]
}
```

`channel` is an explicit signed routing value (`stable`, `beta`, or `nightly`), not an inferred URL path. A stable request accepts only non-prerelease releases in `stable`; beta/nightly require an exact matching `--channel`. Versions use strict SemVer with a leading `v`. The default candidate is the greatest eligible version strictly newer than the running released SemVer. A `dev`/unknown source build cannot select a latest release implicitly: it requires `--version VERSION`. `--version` chooses one exact signed release. A lower target needs both `--version` and `--allow-downgrade`; channel selection never silently downgrades. `minUpdaterVersion` must be no greater than the running updater version. Selection then requires `runtime.GOOS` and `runtime.GOARCH` to match exactly; the six current artifact tuples are the supported initial set.

The manifest's schema range is compatibility evidence, not permission to mutate a database. `check` records one of `compatible`, `migration_required`, or `schema_unknown` after comparing local `version --json` metadata and, only if the user separately runs the existing DB commands, their `migrate status`/`doctor` evidence. `apply` never opens a database. It refuses replacement while `pgbase serve` is detected as this installation's running process; it does not stop a service manager or kill a process.

## 4. Local and HTTPS retrieval

The local form accepts a regular manifest file, detached signature file, and artifact path named by a signed `file:` URL only when `--manifest` mode is chosen. Every local path is opened with `Lstat` checks, copied to the state directory, bounded, then verified by the same signature/hash code as remote input. A successful local verification retains the exact manifest bytes, signature and final artifact digest in the journal.

The remote form accepts one canonical `https` manifest URL with no user info, fragment, opaque form, or non-default unsafe scheme. It derives the signature URL as `MANIFEST_URL + ".ed25519"`; this avoids an unsigned signature-location parameter. Artifact URLs in the signed manifest must be HTTPS and have the same scheme, host, and effective port as the original manifest URL. Tests may use `http://127.0.0.1` or `[::1]` only with `--allow-insecure-loopback`; ordinary HTTP, private key material in query/userinfo, and redirect to another origin are refused.

Each request uses the caller context, a finite default total timeout of two minutes, response-header and body cancellation, and a client redirect callback. Go calls `CheckRedirect` before following redirects; N9 will cap the chain at three and reject a different canonical origin before a follow occurs. [Go HTTP Client redirects](https://pkg.go.dev/net/http#Client). Manifest, signature and artifact limits are respectively 1 MiB, 4 KiB and `--max-download` (default 512 MiB, accepted range 1 MiB–2 GiB). The signed artifact `size` must be positive and no greater than that limit; streaming writes stop at `size + 1`, SHA-256 incrementally, and accept only exact byte count plus digest. Context cancellation, short reads, non-2xx responses, bad redirects, over-limit bodies, and no-space/permission errors remove the staged file and leave the installed binary unchanged.

`--ca-file` is an explicit regular PEM bundle for a private local HTTPS server. It augments the system trust pool only for that invocation and is never written to settings. The native acceptance fixture uses this path with `httptest.NewTLSServer` or an equivalent ephemeral TLS server; it does not need an external account, public certificate, registry, key, or channel.

## 5. Replacement, journal, recovery, and rollback

Before any mutation, the updater takes a nonblocking exclusive installation lock. Unix/Darwin uses `unix.Flock` on the state lock; Windows uses `windows.LockFileEx` with `LOCKFILE_FAIL_IMMEDIATELY|LOCKFILE_EXCLUSIVE_LOCK`. A second `apply`, `rollback`, or recovery returns `replace_busy` and makes no path change. A process exit releases the OS lock; stale journal recovery is therefore serialized by the next invocation.

The journal is a fixed, fsynced JSON record written by temp-file → file sync → atomic replace → parent-directory sync on Unix/Darwin. It contains schema version, operation UUID, immutable target/backup/candidate basenames, old/new build metadata and SHA-256, verified manifest/signature SHA-256, key fingerprint, phase, and timestamp. It contains neither a private key nor URL credentials. Each phase write is durable before the next destructive transition:

1. `verified`: canonical original is a regular executable; manifest/signature/artifact have signature, size, digest, platform and version acceptance.
2. `staged`: candidate is in the executable directory, non-symlink regular file, executable mode copied from original, file synced, and candidate pre-probe (`version --json`) reports exactly the selected version/platform/commit.
3. `backup_created`: original bytes are copied to a named backup, file synced, mode recorded, SHA-256 reread, and backup pre-probe reports the former build.
4. `replacement_started`: state is durable before final platform replacement.
5. `replacement_visible`: canonical path has the candidate; it is reread, regular/mode/digest checked, then post-replacement candidate probe runs from the canonical path.
6. `committed`: candidate probe passed. Backup and evidence remain until explicit `update rollback` or a documented retention cleanup; automatic success cleanup never deletes the only rollback file.
7. `rollback_started` / `rolled_back`: only a verified regular backup with the journalled digest may replace the candidate. Its canonical-path probe must report the former metadata before `rolled_back` is written.

On Unix/Darwin final publication is an in-directory atomic rename with file and parent directory sync. `File.Sync` commits a file's current contents to stable storage according to the Go contract; directory sync errors after rename are indeterminate state, so recovery must inspect hashes and phase rather than assuming rename failed. [Go File.Sync](https://pkg.go.dev/os#File.Sync), [Go Rename](https://pkg.go.dev/os#Rename).

Windows has a separate helper executable and journal path: an active program cannot reliably replace itself. `apply` stages/verifies and launches the helper only after the caller exits; the helper acquires the same lock, confirms the parent process is gone, then uses the Windows-specific replace-with-backup operation. It records every phase and leaves a recovery-required journal rather than guessing if a sharing violation or helper crash occurs. A future Windows implementation must use the platform replacement primitive that preserves the verified original backup; the existing `MoveFileEx` precedent alone is insufficient for that guarantee. The helper and all Windows build-tagged code are implemented and compiled by the six-build gate. Cross-build does not prove host behavior: helper wait, sharing violation, replacement, preserved-backup, journal recovery and old/new probe scenarios are recorded as exact unexecuted Windows-native limitations in this no-Windows-host scope, not as a N9 local-acceptance blocker.

At process start, `update check`, `apply`, `status`, and `rollback` first inspect any journal under the lock. `status` reports the phase without mutating. `check` refuses an unresolved mutation. `apply` either finishes a provably post-probe-successful `replacement_visible` transition or restores only a journal-matching backup; ambiguous/missing/tampered backup returns `recovery_required` or `rollback_failed`, never deletes either binary. `rollback` is explicit and is refused for no journal, active server, incompatible/unknown schema result, missing or modified backup, or active lock. A candidate that exits nonzero, times out, emits malformed/oversized JSON, reports the wrong version/platform/commit, or fails an explicit readiness probe is `probe_failed`; the updater performs the verified rollback before returning failure. A failed rollback leaves both paths and journal for operator inspection.

## 6. Database order and restart boundary

Binary replacement and a PostgreSQL migration are separate recoveries. N9 does not run `migrate up`, `migrate down`, `doctor`, a service-manager command, or automatic restart. It may only inspect a supplied/recorded compatibility result and state that a migration is required.

For a release whose signed schema range covers the current clean history, the local acceptance sequence is: stop the disposable server → `update apply` in a disposable install directory → start the selected binary explicitly → existing `health/ready` and `doctor` checks. For a release requiring a migration, the operator sequence remains: stop/drain → make and verify DB/file backup → run the documented target artifact migration once with auto-migration disabled → retain receipt → activate the signed binary → start → readiness/doctor. If failure happens after a schema transition, binary-only rollback is not called recovery; DB restore and the release-specific compatibility range decide whether the old binary is usable. This preserves the existing [upgrade procedure](../../upgrades.md#upgrade-procedure) rather than creating a false atomicity claim.

## 8. Decisions passed to the integration lead

1. No common migration or shared config/API seam is needed for N9; its state is local file evidence. System migrations 1–40 remain untouched.
2. N9 requires only one later shared CLI table/help edit. N6 also owns CLI work, so integration lead must choose cherry-pick order and resolve that one composition seam after G3; N9 will not create a duplicate CLI agent or modify it during preparation.
3. Existing local six-build outputs are accepted as fixture inputs, but their checksum file and container cosign provenance are not a signed native release channel. N9 creates a local-only native manifest/signature fixture contract.
4. The primary concrete implementation risk is Windows self-replacement. The existing direct `x/sys/windows` version has `MoveFileEx`/lock primitives but no `ReplaceFile` wrapper; a small N9-private Windows binding plus helper/journal is required and must compile in the six-build gate. Its native helper/replacement/recovery scenarios are an exact unexecuted limitation in this environment, not a local-acceptance blocker.

There is no blocker for pre-G3 preparation. N9 product implementation awaits the integration lead's G3 green/assignment signal.
