## 1. 목적, 지원 범위와 PB 차이

사용자가 설치한 **신뢰된 로컬 JS 애플리케이션**으로 PgBase HTTP route, lifecycle/record hooks, 사용자 migration, durable job, 권한을 적용한 record 조회·쓰기, 메일, record-bound 파일 작업을 확장한다. `.js`를 읽고 로그를 출력하는 수준은 완료가 아니다. 외부 Go embedding 앱과 일반 PgBase CLI 모두 같은 runtime/host 서비스를 이용한다.

| 항목 | 채택 계약 | 명시적 차이 |
| --- | --- | --- |
| Engine | pure-Go `github.com/dop251/goja`; G1에서 정확한 pseudo-version/commit·go.sum·라이선스 pin. ES5.1을 기본으로 fixture로 확인한 ES6 문법을 지원표에 추가 | 모든 최신 ECMAScript·Node·browser API를 지원한다고 하지 않음 |
| Modules | CommonJS `.js`/`.json`, confined local source snapshot, VM별 exports cache. `pgbase` native module에만 host API | npm resolver·remote require·Node core/fs/process/exec/network 전역 비지원. ESM/TS는 외부 build에서 CommonJS로 변환 |
| Execution | 동기 handler, 호출마다 새 VM, immutable compiled program cache | PB handler string serialization이나 prewarmed mutable VM pool을 복제하지 않음. Promise/thenable 반환은 명시적 오류; timer/event loop 없음 |
| API | PgBase UUID·lossless numeric·opaque sessions·typed hooks·guarded schema·fenced jobs | PB `$app/$os/$http` API 전체 호환 아님. 별칭만 만들어 호환을 주장하지 않음 |
| Reload | 명시적 개발 supervisor가 유효한 새 source bundle을 확인한 뒤 child app을 drain/restart | production 자동 reload/무중단 hot replacement 아님. migration은 reload로 실행하지 않음 |
| Migration | 기존 `UserMigrationRunner`에 JS callback manifest 합성, 명시적 CLI Up/Down/history | PB serve 자동 적용/기본 auto-record/history source 누락 ledger 삭제와 다름. N1 auto-recorder는 opt-in Go source를 계속 생성 |
| Trust | 로컬 operator가 설치·검토한 코드와 capability 설정. 입력·host 작업·동시 실행 한도 제공 | 적대적 multi-tenant sandbox·VM별 hard heap 격리·uncooperative Go 함수 강제 종료를 보장하지 않음 |

Goja 문서는 pure-Go 구현, runtime의 단일 goroutine 사용, browser/Node event loop 비내장을 설명한다. 현재 API의 `Interrupt`는 native Go 함수 실행 중에는 중단을 강제하지 못하고, `SetMaxCallStackSize`는 call-depth 한도다. 문서상 per-runtime heap quota는 확인되지 않았으므로 hard memory cap을 제품 보장으로 삼지 않는다. [Goja README](https://github.com/dop251/goja), [Goja API](https://pkg.go.dev/github.com/dop251/goja). PB의 현재 Goja/CommonJS 설명 및 migration 동작은 [JS overview](https://pocketbase.io/docs/js-overview/), [JS migrations](https://pocketbase.io/docs/js-migrations/)에서 2026-09-10 확인했다. repo의 PB 비교 pin과 최신 문서의 버전은 구분한다.

구현된 주요 public signatures는 다음과 같다. `JavaScriptOptions`에는 아래 핵심 필드와 admission/input/output limit 필드가 함께 있다.

```go
type JavaScriptOptions struct {
    Directory    string
    Capabilities map[string]bool
    JobServiceSubjects map[string]uuid.UUID
}
// Options.JavaScript *JavaScriptOptions: nil disables the runtime.
func ValidateJavaScript(context.Context, JavaScriptOptions) (JavaScriptManifest, error)
func (a *App) JavaScriptMigrations() ([]UserMigration, error)
func (a *App) ExtensionsForRequest(context.Context) (*ExtensionContext, error)
```

`ValidateJavaScript`는 DB/메일/파일 효과 없이 source graph와 등록표를 검증한다. `New`도 같은 검증 결과/immutable bundle을 사용한다. `JavaScriptMigrations`는 callback 목록을 돌려줄 뿐 실행하지 않는다. embedding은 `RegisteredUserMigrations()`와 합친 뒤 `NewUserMigrationRunner`에 넘기고 중복 ID는 오류다. CLI도 동일 합성 함수를 사용한다. package-global Go migration registry를 app별 JS 등록으로 변경하지 않는다.

`ExtensionContext`는 제한된 `Records`, `Mail`, `Files` operation을 제공하고 내부 admitted identity/context를 보유한다. concrete request/response DTO에는 UUID, opaque ETag/idempotency key, exact JSON bytes/values와 context가 포함된다. `ExtensionsForRequest`는 router가 만든 admission marker가 없는 일반 context를 거절하며 JS JSON에서 principal을 역구성하지 않는다. public route는 credentials가 있어도 anonymous다. service route admission만으로 모든 collection 권한이 생기지 않는다.

Go facade를 기존 HTTP handler의 typed operation adapter와 공유하여 validation/authorization, request Before/After, record transaction hooks, replay, audit/outbox를 동일 순서로 통과시킨다. HTTP decoding과 응답 framing은 router에 남긴다. 동일 request hook을 HTTP와 facade 양쪽에서 두 번 발행하지 않도록 호출 책임을 하나로 정하고 Go API/HTTP/JS 세 경로 비교 테스트를 둔다.

## 4. 애플리케이션 manifest와 loader

`--js-dir`/`PGBASE_JS_DIR`/`Options.JavaScript.Directory`가 opt-in source root를 정한다. root의 `pgbase.scripts.json`은 `format: pgbase.scripts/v1`, API major, 정렬 가능한 entry 목록, route/hook/job descriptor와 migration entry 목록을 가진다. handler는 `{module: "routes/tasks.js", export: "createTask"}`처럼 파일·export 이름으로 참조한다. 이 방식은 함수 source 문자열을 떼어내 closure 의미를 바꾸지 않는다. 등록 수·중복 ID·Go route와의 충돌은 startup error다.

1. root를 절대 경로로 확정하고 manifest/entry/모든 local `.js`·`.json` 파일을 검증하여 immutable byte bundle로 읽는다. absolute/traversal/NUL·root 외부 symlink·특수 파일을 거절하고 실제 열린 파일의 root containment를 확인한다. include 대상 symlink는 보수적으로 모두 거절한다.
2. module resolution은 명시 파일 또는 같은 root 안의 `./`·`../` 상대 `.js`/`.json` 확장만 지원한다. bare name은 `pgbase`만 허용한다. parent `node_modules`, package main 탐색, network, OS 전역 import를 하지 않는다.
3. snapshot 안의 전체 finite module graph를 compile한다. CommonJS cycle은 VM-local partial exports 규약으로 처리하고 test/documentation으로 고정한다. 동적 require도 snapshot에 포함된 경로만 resolve되며 disk fallback은 없다. migration graph는 아래 별도 불변성 규칙을 따른다.
4. descriptor export가 실제 function인지 validation VM에서 확인한다. module top-level에서 host effects와 runtime-dependent registration은 거절한다. 컴파일된 program bytes만 app 단위 공유하고 exports/object/function 값은 runtime 밖으로 공유하지 않는다.
5. source map URL 로딩을 끈다. debugger/type declaration에 쓸 module-relative 이름은 보존하지만 `sourceMappingURL`이 임의 파일/network를 읽게 하지 않는다. dev stack도 root-relative path와 bounded frame만 남긴다.

CommonJS adapter는 `goja_nodejs/require`를 채택하되 `WithLoader`/`WithPathResolver`를 모두 교체하고 runtime별 registry/exports cache를 사용한다. 기본 loader는 filesystem을 읽으며 일부 core native module은 source loader 밖에서 resolve되므로 allowlist만 등록한다. process-global `RegisterNativeModule`이나 광범위 Node module side-effect import는 사용하지 않는다. [공식 require API](https://pkg.go.dev/github.com/dop251/goja_nodejs/require). source bundle과 Goja/require의 정확한 dependency 버전은 함께 pin하며 기본 resolver의 암묵 filesystem 접근이 남지 않는지 fixture로 검증한다.

native binding `.d.ts`는 API major, optional module capability, synchronous 반환, exact scalar/error types를 표현한다. 존재하지 않는 Promise 지원을 선언하지 않는다. JS fixture의 type-check와 외부 TypeScript→CommonJS build를 실행하고 선언과 runtime export inventory가 일치하는지 검사한다.

## 5. 실행·취소·자원 계약

root 호출은 route, Go→JS hook, job 또는 migration의 외부 진입이다. 하나의 VM은 한 goroutine에서만 실행하며 호출 끝에 버린다. VM의 module globals는 같은 호출의 require 사이에서만 유지된다. durable state는 PgBase records/DB에 저장하고 설정 JSON은 invocation별 deep copy로 전달한다. mutable Go pointer/slice/map나 goja.Value를 다른 호출로 전달하지 않는다.

| 항목 | 기본값과 hard contract |
| --- | --- |
| 동시 root/queue | app당 8개, 대기 32개, admission 최대 250ms 또는 더 이른 context deadline. 초과 시 `js_busy`/retryable error, background 무제한 goroutine 금지 |
| 중첩 host→hook | 같은 execution chain slot·deadline·누적 budget을 상속하고 새 VM에서 실행. 최대 깊이 8, 별도 root semaphore를 다시 기다리지 않음. 순환 hook/effect는 더 앞선 mode guard로 거절 |
| JS deadline | route 5초, request/transaction Before 1초, After 1초, module validation 2초. caller/app deadline이 더 짧으면 그것을 적용. request configurable hard ceiling 30초 |
| Job/migration | job은 기존 worker 30초보다 늘리지 않음. migration 기본 60초·설정 hard ceiling 5분, runner/caller/DB timeout 중 가장 짧은 것. transaction 종료까지 취소 연결 |
| Source/stack | module 최대 1MiB, bundle 8MiB/128 files, VM call stack 256. syntax·size·수·depth 초과는 startup/검증 오류 |
| Host calls/data | chain당 256 calls, input/result DTO 1MiB/4MiB, JSON nesting 64, hook scratch state 8KiB. 더 작은 기존 API/schema/body cap을 우선 적용 |
| File resources | invocation당 1개 active opaque stream, 64KiB chunk, 총 byte cap은 configured Files 정책과 invocation quota의 최소값. 종료 시 reader/temp upload를 모두 close/abort. 단일 stream은 storage transition의 shared lease를 끝까지 보유하므로 닫기 전 다른 storage-lock 작업은 fail-fast |
| Shutdown | admission/reload 중단→queued·running cancel→host resource close→VM drain→기존 app Close. default 10초 drain 상한 내 종료 결과와 미종료 host 오류를 보고 |

숫자는 초기 제품 기본값이다. 구현 중 실제 service cap과 충돌하면 기존 더 작은 한도를 보존하고 `.d.ts`/help/docs/tests를 함께 갱신한다. operator가 무제한을 뜻하는 음수/0을 넣을 수 없게 default와 disabled 의미를 분리한다.

실행 owner가 VM을 만들고 cancellation watcher는 context 종료 시 해당 VM에 `Interrupt`만 보낸다. host function은 Go context를 받아 pgx·SMTP transport·file reader에 전달한다. 종료 시 watcher를 join하고 반환 DTO를 완전히 detach한 뒤 VM 참조를 버린다. VM 재사용과 `ClearInterrupt` 경쟁은 만들지 않는다. native 함수 안에서 blocking될 수 있으므로 Go의 deadline 없는 임의 callback을 JS에서 등록하는 API는 제공하지 않는다.

중첩 hook은 bounded fresh VM을 사용하지만 같은 chain의 root slot을 사용하므로 root 8개가 모두 record write→hook에서 대기하는 deadlock을 피한다. 권한/phase/mutation 재진입 금지는 chain-local Go context metadata로 검증하며 JS가 값을 바꿀 수 없다. After의 기존 detached context에서도 origin capability·depth/budget은 안전하게 복사하되 app shutdown 취소를 별도로 연결한다.

제한은 CPU loop·call depth·host IO·입장/결과 메모리를 제어한다. JS가 짧은 시간에 거대한 array/string을 만들거나 native Go 함수가 context를 무시하는 경우까지 process 생존을 보장하지 않는다. 메모리 폭주 시험은 disposable child process/OS resource bound에서 실행하고 서버 본체를 OOM시키지 않는다. hard heap 격리가 필요한 untrusted scripts는 별도 process/제품 설계가 필요하며 N6의 숨은 완료조건으로 주장하지 않는다.

## 6. Binding과 phase별 권한

native API는 `require("pgbase")`의 명시적 object다. Go struct를 `ToValue(app)`처럼 반사 노출하지 않고 함수별 인자 검사와 detached DTO encode/decode를 사용한다. operator의 `Capabilities` 설정은 script manifest가 권한을 요청할 수는 있어도 늘릴 수 없는 ceiling이다. request authority와 capability가 교차 적용된다. background job은 Go가 startup에 부여한 named scope를 사용하고 JS에서 user/admin/service ID를 지정해 위조할 수 없다.

| Binding | 제공 동작 | 실서비스와 보안/실패 경계 |
| --- | --- | --- |
| `request` / `response` | method/path params/query·허용 header·bounded body·credential-free principal, status/header/JSON·bytes 반환 | 기존 CustomRoute admission/body/response cap. Authorization/cookie/session secret은 기본 DTO에서 제외. hop-by-hop·Set-Cookie는 제공하지 않고 app auth API가 세션을 소유 |
| `records` / `db` | catalog-bound list/get/create/update/delete/batch, structured filter/sort/page; `db`는 같은 제한 query facade의 별칭·문서화된 entry | `recordops/query/recordaccess`, N4 options/modifiers/관계·exact values, ETag/idempotency/replay, N5 request+mutation hooks. request 일반 raw SQL/pgx pool 비노출 |
| `mail` | operator가 허용한 generic mail send, Message DTO·bounded attachment/recipient | 기존 hooked mailer와 transport/context. SMTP 설정·credentials 접근 없음. 임의 auth token 발급/목적 위조 API 없음. 같은 mail hook 안에서 다시 send 거절 |
| `files` | record-field attachment list/upload/delete/token/open/transform, bounded byte stream handle | 기존 filestore authorization/reference/cleanup/variant contract. raw `OpenObject`·storage key·host path·driver 설정 비노출. 취소·실패 시 temp/reservation 정리 |
| `jobs` | manifest name/schedule/timezone/capability + exported handler, run metadata | `ScheduledJob` 및 기존 durable service. handler 등록 후 claim; 제거/변경은 명시 restart/reconcile, admin persisted schedule 보존 |
| `migration` | 아래 tx-scoped `query/exec`, canonical snapshot apply, immutable before/after metadata | `UserMigrationRunner` callback 동안만 유효한 handle. callback 종료/취소 후 재사용 실패. main pool/transaction commit/rollback 직접 호출 비노출 |
| `log` / values | bounded level/message/허용 metadata, exact numeric/UUID helpers, stable error constructors | requestID/module/handler만 자동 첨부. arbitrary object dump·credential/env/DB URL·absolute path 금지. app logger와 error redaction 경유 |

읽기/외부 효과 권한은 호출 phase마다 다르다.

| Phase | 허용 | 거절/주의 |
| --- | --- | --- |
| Load/registration | local pure module evaluation·typed descriptors | DB/mail/file/jobs 실행·현재 사용자 접근·runtime-dependent registration |
| Route/job body | scope에 맞는 records/mail/file, 기존 job semantics | service admission을 admin으로 승격, 사용자 권한 우회, raw SQL |
| Request/transaction Before | typed input patch·veto·필요한 bounded 읽기 | record writes 재진입·mail/file mutation/job schedule side effects. retryable Before에서는 외부 효과 불가 |
| After observation | 최종 DTO 관찰·bounded log, 허용된 별도 effect는 명시적 best effort | commit rollback/veto 불가. record mutation hook은 before/after 모두 기존 write 재진입 금지. mail/file hook의 자기 effect 순환 금지 |
| Migration Up/Down | 공급받은 tx의 parameterized SQL·managed snapshot helper | 독립 DB connection·명시 commit/rollback·mail/file/job/HTTP/OS 효과. source checksum/ledger/physical validation 우회 |

큰 수는 decimal 문자열 기반 `ExactNumber`와 raw JSON token codec으로 이동한다. `numeric`/int64/sequence ID/JSONB 숫자를 Go→JS Number→JSON으로 왕복하지 않는다. UUID는 canonical string, timestamp는 timezone이 명시된 string, bytes는 opaque stream/chunk이며 임의 object를 raw Go byte buffer로 변환하지 않는다. field options, null/omitted, password redaction은 HTTP와 같은 기준이다.

SMTP body/수신자에는 실제 검증 링크 등 애플리케이션 비밀이 포함될 수 있다. 신뢰된 mail hook은 문서화된 Message를 수정하므로 이 내용을 일괄 secret-free라고 주장하지 않는다. auth lifecycle metadata에는 비밀번호/OTP/raw token을 주지 않고, 어느 hook의 payload도 자동으로 로그에 기록하지 않는다.

## 7. Go hooks와의 합성 계약

N6는 [N5 event 대조표](../../lifecycle-parity.md)의 모든 노출 event를 binding inventory로 만든다. `app.boot/serve/terminate`, collection·record mutation, typed CRUD request·Batch/import, mail/purpose, files, auth, realtime, settings, backup이 대상이다. 임의 ORM 내부 model validate/execute 이벤트는 기존과 마찬가지로 지원하지 않는다.

- Go `HookRegistry`에 JS adapter를 같은 priority 의미로 등록한다. 동률 순서는 Go 등록 순서 뒤에 manifest의 정렬된 JS descriptor 순서로 고정하고 문서화한다. `Before`는 input validation/인가를 대체하지 않으며 patch 후 기존 service가 다시 검사한다.
- patch는 payload별 allowlist만 적용한다. actor/record/file identity, Batch sidecar/op identity, idempotency/checksum/승인 import body, purpose·storage config는 읽기 전용이다. 예상치 못한 속성/수정은 `js_invalid_patch`로 거절한다.
- lifecycle Before와 After는 같은 Go registry snapshot과 같은 source bundle을 참조한다. 두 JS VM은 별도이며 명시적인 bounded JSON `state`만 paired event에 전달할 수 있다. mutable module global이 After에 남는다고 가정하지 않는다.
- record `MutationHook`는 immutable EventID/record/actor/version metadata·veto만 제공한다. transaction retry에서는 Before가 반복되고 최종 commit 후 After가 한 번 관찰되는 기존 의미를 보존한다. request replay와 Batch request-wide event 횟수도 기존 계약을 따른다.
- Go panic은 기존 boundary에서 error로 변환되고 JS throw/interrupt는 typed Go error가 된다. Go hook과 JS hook 중 하나가 veto한 뒤 최종 After 결과가 정확히 하나로 전달되는지 검증한다. After throw는 원래 성공/실패 응답을 바꾸지 않고 bounded observation error로 기록한다.
- app Close는 terminate hook veto가 있어도 resource cleanup을 계속한다. 생성자·Start·Run·Close의 구분과 route startup sealing을 바꾸지 않는다. realtime/file download처럼 오래 열린 event의 After는 기존 EOF/close/cancel에 연결된다.

Go 임베더는 기존대로 신뢰된 Go hooks를 작성할 수 있다. JS wrapper는 임베더가 직접 등록한 uncooperative Go hook을 강제 종료하거나 Go의 OS/network 권한을 제한하지 못한다. 이 한계와 JS 자체 quota를 구분하여 문서/시험에 기록한다.

## 8. JS 사용자 migration과 N1 보존

manifest migration entry는 ID·module Up/Down export·API major·선택적 canonical Before/AfterSnapshot·IrreversibleReason을 가진다. 변경 적용은 기존 `UserMigration{ID, Source, Up, Down, ...}`로 adapter가 만들어 `NewUserMigrationRunner`에 전달한다. Go/JS ID 중복은 startup/CLI 구성 오류이며 둘을 합쳐 ID순으로 처리한다. JS라는 이유로 기존 적용 이력을 바꾸지 않는다.

**Source authority:** migration마다 별도의 frozen module bundle을 만든다. entry와 허용된 모든 migration dependency의 normalized relative path·byte length·정확한 bytes, format/API version·migration descriptor를 결정적인 envelope로 직렬화하고 그 전체를 `Source`로 삼는다. Go migration은 기존 exact `.go` Source를 유지한다. migration의 local imports는 manifest에 명시된 migration 전용 dependency 집합 안에서만 가능하며 일반 app code·동적 disk require·환경 config 접근은 금지한다. 같은 dependency를 고치면 그것을 포함한 적용 migration이 checksum mismatch가 되어야 한다. ledger checksum의 source 형식/검사 출력에도 JS bundle임을 명시한다.

1. `migration up|down|list|history|history-sync`에 `--js-dir`을 연결하되 source 선택은 모두 같은 bundle reader를 사용한다. `serve`는 user migration을 암묵 실행하지 않는다. `js check`는 DB와 ledger를 건드리지 않는다.
2. Up/Down callback은 fresh VM과 tx-scoped native handle을 받고 parameterized `exec/query`와 `applySnapshot(before,after)`를 수행한다. SQL은 이 trusted callback의 기능이며 일반 request용 SQL Console과 공유하지 않는다. 기존 runner의 system/schema lock·commit/ambiguity·validation·cache refresh를 보존한다.
3. managed collection/field 변경은 `ApplyUserMigrationSnapshot` 경로를 사용하여 rename/relations/View/index/N4 options를 보존한다. SQL `exec/query`는 extension-owned tables/data의 명시적 관리 작업에 사용한다. PgBase record DML을 직접 SQL로 실행하면 audit/outbox/record hooks를 자동 재현한다는 주장을 하지 않으며 supported CRUD 경로로 안내한다.
4. arbitrary trusted SQL의 모든 외부/extension 효과가 PostgreSQL rollback으로 되돌아온다고 보장할 수 없다. JS host surface에서는 외부 IO를 차단하고 existing runner의 ledger/control-schema 방어를 유지한다. 고의적인 Go callback/DB extension 코드는 sandbox 대상이 아니다.
5. Down이 없는 경우 실행 전에 이유를 반환하며 데이터 손실 작업을 가역으로 속이지 않는다. 지원하는 Down은 실제 isolated DB에서 roundtrip과 failure rollback을 입증한다. history-sync는 현재 안전 조건/증거를 통과한 경우만 사용하고 소스가 없다는 이유로 applied history를 삭제하지 않는다.
6. N1 `migration create/snapshot/diff`와 관리자 opt-in auto-recording은 Go source 생성/내구 outbox를 유지한다. JS 앱을 쓰는 사용자도 생성 Go migration을 compiled manifest에 포함할 수 있으며 `.js` 자동 생성이라고 오표시하지 않는다. 기존 recover/auto-status·source-write failure 복구를 회귀 검증한다.

JS migration metadata와 source envelope API version을 문서화하고 지원하지 않는 major는 source/DB 변경 전에 거절한다. engine 버전을 바꿀 때는 저장된 JS migration fixture를 재실행하여 syntax/host semantics 호환을 검토한다. JS runner 추가 때문에 시스템 migration 1–40을 편집하거나 새 ledger를 만들 필요는 없다.

## 9. Jobs, effect retry와 개발 reload

JS job descriptor는 기존 `ScheduledJob`의 name/schedule/timezone/handler로 변환한다. `JobsEnabled`가 꺼져 있는데 job이 요구되면 명확한 startup error로 알리고 무시하지 않는다. 시작 시 code handler를 등록한 다음 worker가 durable job을 claim한다. admin이 DB에서 수정한 schedule/enabled 상태는 restart/reload에서 기본값으로 덮어쓰지 않는다. interval뿐 아니라 기존 five-field cron·timezone 경로도 검증한다.

handler throw/cancel은 기존 job 실패/lease/retry 결과에 반영한다. `JobRun`은 JobID/FenceGeneration/RunKey와 ScheduledAt/OccurrenceKey를 준다. occurrence key는 첫 claim에서 예정 시각을 `last_scheduled_at`에 고정하고 실패 claim에서는 보존하며, 성공 뒤 attempts가 0인 다음 claim에서 새 예정 시각으로 교체한다. one-effect-per-occurrence 작업은 occurrence key를 idempotency key로 쓰고 fence는 stale attempt가 새 상태를 덮어쓰지 못하게 동일 DB transaction에서 검증한다. 메일 전송 직후 crash가 나면 외부 전달은 중복될 수 있으며, SMTP fixture 한 번 관찰을 exactly-once 보장으로 확대하지 않는다. durable effect가 필요한 예제는 app task/outbox record와 idempotent 소비 방식을 함께 보여준다.

개발 reload는 `js serve --watch` supervisor가 디렉터리 snapshot hash를 debounce해 감시한다. 전체 prospective bundle을 DB 효과 없이 검증한 후 child에게 shutdown을 요청하고 bounded drain 뒤 새 child를 시작한다. syntax/type/route conflict 실패 시 기존 child를 유지하고 수정 위치를 표시한다. 유효한 변경에서 port를 다시 열 때 짧은 중단이 있으며 새 child startup 실패 시 마지막 검증된 source snapshot으로 복귀하거나 명확한 stopped 상태를 보고한다. **실패한 새 source를 두고 기존 app이 계속 실행되는지 UI/log에서 구분**한다.

supervisor는 두 child가 동시에 jobs를 실행하거나 listener를 소유하지 않게 순서를 고정하고 startup generation/source digest를 상태 출력에 담는다. 전체 bundle을 child에 고정 전달하여 검증과 실행 사이 디스크 수정 race를 막는다. production `serve`는 이 supervisor를 사용하지 않으며 reload가 migration Up 또는 N1 source publication을 대신하지 않는다. N9 updater와 개발 child restart는 별도 module/CLI다.

## 10. 오류와 운영 계약

| 원인 | 호출자 결과 | 변경·후속 처리 |
| --- | --- | --- |
| source syntax/export/path/capability 오류 | startup/check configuration error, CLI exit 2 | DB 연결/route 등록/worker 시작 이전 거절 |
| queue/VM deadline/caller cancel/quota | `js_busy`, `js_timeout`, `js_canceled`, `js_limit_exceeded`; context cause 보존 | 실제 service transaction 취소·rollback/ambiguous commit 규약 유지. client disconnect 후 성공 rollback을 꾸며내지 않음 |
| before veto/invalid patch | typed application validation error 또는 `js_invalid_patch` | 재검증 전에 거절, record/schema commit 없음 |
| host domain error | 기존 status/code/details·requestID 전달 | password/SQL parameter/credential/absolute path 제거, API의 non-disclosure 의미 보존 |
| uncaught JS throw/native panic | `js_execution_failed`, bounded internal module/handler/stack log | HTTP에 raw stack/환경 값 반환 금지. job 실패·migration rollback은 각 기존 service 경로 |
| After failure | observation log/metric | 이미 정해진 commit/응답/restore activation을 변경하지 않음. durable retry를 암묵 보장하지 않음 |

취소가 commit과 경합하면 기존 API의 operation/history/idempotent retry로 최종 상태를 확인한다. timeout이라고 이미 commit된 DB 상태를 지운 것으로 응답하지 않는다. metrics는 source digest·handler ID·phase·queue/execution duration·quota/timeout 분류를 기록하고 user payload나 source 전체를 label로 넣지 않는다.

권장 focused 실행 묶음은 신규 `internal/jsvm` unit/race, `pgbase`의 `JavaScript|Extension` integration tests, 관련 `internal/cli` focused tests와 외부 fixture runner다. 통합 담당이 맡은 `./...` 전체 suite를 N6 worktree에서 반복하지 않는다. UI/SDK를 수정했다면 해당 변경의 focused 검사까지 담당하고 공통 생성물은 lead에게 위임한다.
