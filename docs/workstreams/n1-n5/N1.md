## Concrete design

1. Add `pgbase.schema-migration/v1`, a canonical migration snapshot distinct from the existing portable schema export. It contains logical collection definitions, stable field IDs, relations by collection name, views and dependencies, indexes, access flags, rules, and the complete `FieldOptions` JSON object. It excludes physical table/index/storage names, timestamps, administrator identity, credentials, token secrets, password values, record data, and file bytes. Canonical JSON sorts collections, dependency sets, and other set-like options while preserving field ordinal, index field order, and view projection order.
2. Add a deterministic diff that matches retained fields by stable ID so a name change is a rename. It emits dependency-ordered operations: remove dependent views/indexes and outgoing relations before destructive base changes; create scalar base collections before relations; update exact fields/indexes; then create views in topological order. The reverse diff uses the same compiler. Collection deletion and field deletion/type replacement are marked as irreversible because a later Down cannot restore removed values. Down operations that drop objects created by Up remain executable but carry an explicit data-loss warning.
3. Generate compilable Go migration source containing canonical before/after snapshots and registration metadata. Generated `Up` and supported `Down` call an exported `pgbase` transaction helper; irreversible Down returns a typed error with the generated reason. Source bytes remain the checksum authority. Generation uses exclusive create plus an atomic temporary-file rename for auto materialization; identical retries accept the existing byte-identical file and reject conflicts.
4. Extend CLI with collection snapshot, snapshot diff/source generation, source/history comparison, and explicit history sync. History sync may adopt only the next compiled migration, only when it carries generated snapshot metadata, and only after the current database snapshot equals that migration's expected after snapshot under the user/schema advisory locks. It inserts the checksum-pinned ledger row without running callbacks or advancing schema version. Missing source, checksum mismatch, non-prefix history, and history-only rows remain visible and cannot be silently repaired.
5. Add opt-in administrator mutation recording via `Options.UserMigrationAutoRecordDirectory` and `PGBASE_USER_MIGRATION_AUTO_RECORD_DIR`. The schema service captures canonical before/after snapshots and queues exact generated source in a migration-40 ledger in the same transaction as the schema mutation. Source writing happens only after a successful DB commit. A pending row survives process/request failure and a background/CLI recovery pass writes it idempotently. A source-write failure never rolls back or misreports the already committed schema operation; status exposes pending/conflict/error state. If DB commit fails, no durable row exists and no source is written.
6. Apply helpers operate entirely inside the user migration's supplied `pgx.Tx`, share PgBase's schema lock order, validate the exact starting snapshot, execute DDL and metadata atomically, update access/rules, and let the existing runner advance `schema_state` once with the user migration ledger. Failed DDL, policy writes, validation, or snapshot mismatch rolls back both physical and metadata changes.
7. N4 option compatibility is obtained by canonical serialization of the complete schema-domain `FieldOptions`, not a duplicated allowlist. N5 request hooks stay separate from the durable recorder; the recorder is part of the schema transaction and post-commit materializer.
