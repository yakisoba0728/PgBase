# N5 — request and lifecycle hooks

## Design

N5 extends the existing typed `pgbase` lifecycle adapter rather than changing the
transactional model hooks.  Each new hook receives a purpose-specific, credential-free
payload and runs at an explicit boundary:

| Area | Hook boundary | Payload mutability | Veto / outcome |
| --- | --- | --- | --- |
| record list/view/write | Immediately after route admission and before the typed service action; collection/rule authorization remains in that service | Request metadata and write input are mutable and revalidated by the service; authenticated principal, record identity and idempotency identity are immutable observations | A returned error vetoes before the service action; cancellation is propagated |
| batch/schema import | Once for the whole decoded, route-admitted request and before any item/schema mutation | Batch operations are mutable and revalidated/authorized by the service. Schema preview document is mutable; guarded schema-apply document is observational/veto-only to preserve checksum and replay identity. Principal and idempotency identity are immutable observations | A returned error vetoes the whole request before work starts |
| mail send | After recipient/action authorization and rendering, immediately before transport delivery | Subject/body/recipient metadata mutable; transport configuration and credentials are never present | A returned error prevents delivery; transport result is reported |
| file token/download/transform | After file access authorization and before token issuance, streaming, or derivative creation | Credential-free immutable observation; file identity, actor, variant and storage configuration cannot be changed | A returned error prevents that operation |

Panics become returned internal errors; request cancellation is never converted into a
retry.  Hook registration is process-local.  A request retry/replay invokes the hook
again with a new invocation ID but the same immutable idempotency identity where one
exists.  Pre-action hooks cannot claim a committed result.  Existing post-commit hooks
remain best-effort and are not durable delivery or N1 migration-mutation recording.

N5 intentionally does not implement PocketBase's arbitrary ORM model
validate/execute/success/error callbacks: PgBase exposes typed API/service boundaries
only, preserving service-owned transactions and authorization.

## Acceptance checklist

- [x] CRUD list, view and write hooks run on real API paths with documented order,
  mutable input boundary and immutable authorization boundary.
- [x] Batch and schema-import hooks run once per complete request and can veto before
  partial work.
- [x] Purpose-specific mail and file hooks cover send, token, download and transform
  paths without exposing credentials.
- [x] Panics, cancellation, retry/replay and final commit/transport outcomes have
  focused API/service integration evidence.
- [x] `docs/lifecycle-parity.md` and user-facing feature documentation describe N5
  scope, non-goals and post-commit/durable-delivery distinction.

## Limitations

- Hooks are process-local and execute again on a client retry/replay. They are not an
  outbox and must not be used for durable external delivery.
- PgBase deliberately does not add PocketBase's arbitrary ORM model
  validate/execute/success/error callback surface.
- Guarded schema-import apply hooks can inspect and veto the document but cannot mutate
  it, because doing so would invalidate the caller's sealed checksum and replay identity.
