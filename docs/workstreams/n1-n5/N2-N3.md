### N2 design

Add `Options.PublicDir string` and `Options.PublicSPAFallback bool`, configured by
`PGBASE_PUBLIC_DIR` and `PGBASE_PUBLIC_SPA_FALLBACK`, and expose the same values
through `pgbase serve --public-dir DIR [--public-spa-fallback]`. An empty public
directory disables this feature. The directory must be an absolute, existing
directory resolved with `EvalSymlinks`; resolution failures reject startup.

The application mounts the public handler as the closed router's final
fallback.
Therefore `/api`, `/api/...`, `/admin`, `/admin/...`, health endpoints,
`/metrics`, and registered custom routes retain their present behavior,
including their 404 responses and method-specific 405 responses. The public
handler only considers unmatched non-reserved paths. `GET` and `HEAD` are
supported; other public methods return 405. It will reject malformed/escaping paths, preserve a 404
for an asset-shaped request whose file is absent, and serve the configured
`index.html` only for a navigation-shaped missing path when SPA fallback is
enabled. Directories (including `/`) resolve only to `index.html`; a directory
without it is 404. Every opened file is checked with `EvalSymlinks`, then
opened and re-statted before serving, and must remain beneath the resolved
public root. In-root symlinks are allowed and links that escape it are not
served. `http.ServeContent` supplies MIME, byte
ranges, Last-Modified, and HEAD behavior. The handler will add conservative
cache policy: immutable assets with a content hash get long immutable caching;
HTML and unhashed files get `no-cache`.

Acceptance checklist:

- [x] Go `Options`, environment, and `serve` flags configure the feature.
- [x] API/admin/custom routes win and API 404 remains JSON/API 404.
- [x] Existing/missing assets, SPA deep link, missing directory, traversal,
  symlink escape, MIME/cache/HEAD are covered by focused HTTP tests.
- [x] An `httptest` browser-style deep-link refresh checks a real built asset
  and fallback document without an external static server.

### N3 design

Add an `admin upsert` command: create when the normalized email is absent;
otherwise change the password using the existing password-reset service.
`admin update` is a compatibility alias for `upsert`, explicitly requiring a
password and thus having no non-password update semantics. Add `admin delete`
with normalized email lookup. All password-changing/deleting operations
invalidate that administrator's sessions; delete and upsert/reset are
transactional and never leave partial changes. Delete refuses the last active
administrator. Existing `create` remains create-only and duplicate failure
semantics remain intact.

N3 uses confirmed migration 39: per-administrator TOTP
secret state and normalized CIDR allow-list. The CLI will use `admin otp
enable|disable` and `admin ip allow|deny|list`; enable takes a base32 TOTP
secret on stdin to avoid command-line disclosure, and disable removes the
secret. IP allow-lists are deny-by-default once non-empty, accept canonical
CIDRs only, and apply to login and every authenticated administrator request
(session use is rechecked). The client IP comes from the existing trusted-proxy
resolution, so untrusted `X-Forwarded-For` cannot bypass the policy. OTP is a
second login submission: a valid password without `otpCode` receives the
`otp_required` response; resubmitting the same login payload with a current
RFC 6238 six-digit `otpCode` issues the session. This deliberately does not implement PocketBase email OTP,
per-admin roles, or WebAuthn; those differences will be documented.

Acceptance checklist:

- [x] CLI upsert/delete/update alias use the shared admin service; usage and
  exit-code behavior are covered.
- [x] OTP/IP CLI management has validation, idempotent insert/delete semantics,
  deterministic listing, and isolated DB execution.
- [x] Actual login and subsequent session requests enforce OTP/IP policy in
  the tagged HTTP acceptance test on isolated PostgreSQL.
- [x] Password reset/upsert/delete invalidate sessions; deleting the last
  active admin fails without changing the database.
- [x] Focused isolated PostgreSQL integration tests prove route precedence,
  OTP/IP login and session enforcement, CLI management, password/session
  invalidation, and last-admin protection.
