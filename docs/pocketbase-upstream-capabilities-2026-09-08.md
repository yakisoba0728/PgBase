# PocketBase upstream capability baseline (2026-09-08)

Scope: upstream PocketBase only. This note supplies a comparison baseline; it does **not** estimate PgBase progress.

## Version pin

- **Fact:** the latest GitHub release observed on 2026-09-08 was [`v0.40.3`](https://github.com/pocketbase/pocketbase/releases/tag/v0.40.3), published 2026-09-06 17:33 UTC. The tag resolved to commit [`5684ee24f1e88f71a2ede73d20cf547fbd509e16`](https://github.com/pocketbase/pocketbase/tree/5684ee24f1e88f71a2ede73d20cf547fbd509e16). The official docs also identified themselves as v0.40.3 ([docs landing page](https://pocketbase.io/docs/)).
- **Fact:** PocketBase describes itself as a single portable Go backend with embedded SQLite, realtime subscriptions, file/user management, an admin dashboard, and a REST-ish API ([README pinned to the commit](https://github.com/pocketbase/pocketbase/blob/5684ee24f1e88f71a2ede73d20cf547fbd509e16/README.md)). It remains pre-1.0 and explicitly does not guarantee full backward compatibility ([official docs](https://pocketbase.io/docs/)).

## Capability baseline

| Area | Upstream capability at the pinned baseline |
|---|---|
| Data model | Three collection types: **Base** (ordinary mutable records), **View** (read-only SQL `SELECT` results, including aggregations), and **Auth** (Base plus user/auth fields and methods). Collections are backed by generated SQLite tables and are managed through the dashboard, APIs/SDKs, or Go/JS migrations ([collections](https://pocketbase.io/docs/collections/)). View collections do not emit realtime changes because they have no create/update/delete operations. |
| Authentication | Stateless bearer-token auth; auth methods are configurable per Auth collection. Built-ins cover identity/password, OAuth2 providers, email OTP, and optional MFA requiring two different enabled methods. Account workflows include email verification, password reset, and authenticated email change; successful password reset/email change invalidates prior record tokens ([authentication](https://pocketbase.io/docs/authentication/), [record auth APIs](https://pocketbase.io/docs/api-records/#auth-record-actions)). Superusers bypass collection API rules; OAuth2 is unavailable for the `_superusers` collection. |
| Records and access control | REST/SDK record list/search, view, create, update, delete, plus filtering, sorting, pagination and field expansion ([record APIs](https://pocketbase.io/docs/api-records/)). Every collection has `listRule`, `viewRule`, `createRule`, `updateRule`, and `deleteRule`; rules are both authorization checks and record filters, with locked, public, or expression-based modes ([API rules](https://pocketbase.io/docs/api-rules-and-filters/)). |
| Batch writes | `/api/batch` supports transactional create, update, upsert and delete in one request, including multipart file uploads. It is disabled until explicitly configured; all items share one auth state and execute in a single read/write transaction ([batch API](https://pocketbase.io/docs/api-records/#batch-create-update-upsert-delete-records), [pinned implementation](https://github.com/pocketbase/pocketbase/blob/5684ee24f1e88f71a2ede73d20cf547fbd509e16/apis/batch.go)). |
| Relations | Single and multi-value relation fields; append/prepend/remove modifiers; forward and back-relation filter/sort/expand; nested paths up to six levels. Back-relation expansion is capped at 1,000 records per field ([relations](https://pocketbase.io/docs/working-with-relations/)). |
| Files | Multipart uploads on record create/update, multi-file mutation helpers, generated file URLs, protected files gated by short-lived file tokens plus the record View rule, and on-demand image thumbnails. Storage defaults to local `pb_data/storage` and can switch to S3-compatible services ([files](https://pocketbase.io/docs/files-handling/)). |
| Realtime | SSE endpoint with subscriptions for a whole collection or one record; create/update/delete events are checked through ListRule/ViewRule respectively. SDKs expose subscribe/unsubscribe helpers, and server extensions can publish custom topics ([Realtime API](https://pocketbase.io/docs/api-realtime/), [JS realtime messaging](https://pocketbase.io/docs/js-realtime/)). |
| Extensibility and jobs | The binary embeds a Goja-based JavaScript runtime and loads `pb_hooks/*.pb.js`; JavaScript can register routes and lifecycle/request/model hooks. PocketBase can also be imported as a Go framework with typed event hooks and custom routes ([JS overview](https://pocketbase.io/docs/js-overview/), [JS hooks](https://pocketbase.io/docs/js-event-hooks/), [Go hooks](https://pocketbase.io/docs/go-event-hooks/), [pinned Go example](https://github.com/pocketbase/pocketbase/blob/5684ee24f1e88f71a2ede73d20cf547fbd509e16/examples/base/main.go)). Both extension modes support cron-like scheduled jobs; jobs are visible and manually triggerable in the dashboard ([JS scheduling](https://pocketbase.io/docs/js-jobs-scheduling/), [Go scheduling](https://pocketbase.io/docs/go-jobs-scheduling/)). |
| Client SDKs | Two official clients: JavaScript for Browser/Node.js/React Native and Dart for Web/Mobile/Desktop/CLI ([pinned README](https://github.com/pocketbase/pocketbase/blob/5684ee24f1e88f71a2ede73d20cf547fbd509e16/README.md), [JS SDK](https://github.com/pocketbase/js-sdk), [Dart SDK](https://github.com/pocketbase/dart-sdk)). Other languages must use community SDKs or the HTTP API. |
| Deployment and operations | Standalone executable with no required external service; built-in automatic TLS can serve a domain directly, or it can sit behind a reverse proxy. The docs provide systemd and Docker examples, while noting there is **no official Docker image**. Persistent state lives in `pb_data`; built-in backup/restore supports local or S3-compatible backup storage. Production controls include SMTP configuration, a built-in rate limiter, superuser IP allowlisting, optional superuser MFA, and settings encryption ([production guide](https://pocketbase.io/docs/going-to-production/)). |

## Interpretation boundary

- **Facts** above are claims stated in first-party documentation or present in source at the pinned commit.
- **Assumption for comparison:** “PocketBase parity” should mean user-visible behavior plus the associated authorization, operational, and extension surfaces in this table. Merely exposing similarly named endpoints is insufficient unless the PgBase audit adopts a narrower definition.
- **Not assessed here:** UI completeness within each dashboard screen, performance equivalence, compatibility with PocketBase SDK edge cases, migration fidelity, and production maturity. Those require local PgBase inspection and behavioral tests.
